End-to-End Mobile Eye-Tracking System

Personal Project · Jul – Nov 2025

GitHub Article on Medium
Python · PyTorch · TensorFlow Lite · Flask · Computer Vision

Overview

A personal passion project built from scratch over the summer of 2025. The goal was to build a complete gaze estimation system — from raw data to a real-time mobile prototype — without using any off-the-shelf gaze estimation libraries. The project uses the GazeCapture dataset from MIT CSAIL, which contains over 500,000 labelled frames collected from more than 2,000 participants using iOS devices.

Beyond the technical output, the project was a deliberate exercise in learning how end-to-end machine learning systems actually work — covering data engineering, model architecture, training infrastructure, regularisation strategy, and production deployment.

Data Pipeline

The raw GazeCapture dataset contains 819,428 labelled frames. After filtering out non-vertical orientations and samples with invalid face or eye detections, the working dataset was reduced to 515,459 frames. A scalable augmentation pipeline then generated over 1.5 million training frames from these.

Each sample was processed by cropping the face and bilateral eye regions and resizing to 64×64 pixels, followed by brightness and contrast jitter, grayscale conversion, and Gaussian noise injection. All metadata was consolidated into a single CSV index with a deterministic train/validation/test split to ensure reproducibility across runs.

Model Architecture

The model uses a three-branch CNN — one branch each for the face crop, left eye crop, and right eye crop. Each branch consists of three convolutional blocks with 32, 64, and 128 filters respectively, using 3×3 kernels, ReLU activations, and max pooling after each block. This lets the network progressively learn higher-level spatial features from each input region independently.

The three branch outputs are flattened to 128 units each and concatenated into a single 384-unit representation. This fused vector passes through a dense layer (128 units) before producing the final two-dimensional output representing the predicted gaze point (X, Y) in screen coordinates.

Five progressive model variants were trained and evaluated: a baseline, L2-regularised, dropout-regularised, early stopping with dropout and L2, and a batch-normalised production model. Each iteration isolated the effect of individual regularisation techniques.

Training & Results

Models were trained on RunPod GPU cloud infrastructure. The final model achieved a mean absolute error of 1.409 cm on the held-out test set. The most impactful improvements came from applying a dropout rate of 0.3 and early stopping with a patience of 8 epochs, which curbed overfitting without sacrificing too much training performance.

A key practical insight was that regularisation techniques should be introduced one at a time — applying dropout, L2, and batch normalisation simultaneously makes it impossible to attribute improvements to any single technique.

Deployment

The trained model was converted to TensorFlow Lite and served through a lightweight Flask web application accessible over HTTPS (for mobile camera access). At inference time, OpenCV's Haar Cascade classifiers detect the face and eye regions in each camera frame, the same preprocessing pipeline from training is applied to ensure distribution consistency, and the predicted gaze coordinates are denormalised back to screen space.

The prototype includes a four-corner calibration UI to map normalised model predictions to physical screen coordinates, and a live gaze point overlay rendered in real time.

Key Lessons

Building this system end-to-end produced a number of practical lessons that courses and tutorials rarely cover:

  1. Your dataset doesn't just support your project — it defines it. The choice of training data shapes everything downstream.
  2. Data preparation dominates real ML work. Most effort goes to data handling, not modelling.
  3. Organise messy data early. Consolidating everything into a single structured index pays off throughout the project.
  4. Start with a simple baseline before optimising. Initial results reveal where to focus effort.
  5. Prototype locally on a small subset, then scale to cloud GPU infrastructure for full training runs.
  6. Regularisation improves generalisation specifically — it trades some training accuracy for better held-out performance.
  7. Bias-variance trade-offs are unavoidable. Finding the right balance requires iteration, not a formula.
  8. Early stopping is one of the most practical regularisation tools — simple, interpretable, and effective.
  9. Add regularisation techniques one at a time. Simultaneous changes make attribution impossible.
  10. Real problems drive real learning. Building something you genuinely care about produces far more insight than structured exercises.
